# Nexora Nexus — Backend Security Architecture & Implementation Foundation

## 1. Executive Summary

This document establishes the binding security specifications for the Nexora Nexus backend platform (Cloudflare Workers + D1 + R2 + Razorpay). All future API endpoints, authentication flows, and data mutations must adhere to these policies.

---

## 2. Authentication & Authorization Policies

### 2.1 Admin Provisioning
- **Strictly No Public Admin Registration**: The public registration endpoint will only ever accept enrollment for the `intern` role.
- **Controlled Elevation**: Administrative (`admin`, `reviewer`, `mentor`) accounts must be provisioned out-of-band via secure database seeding scripts, CLI commands (`wrangler d1 execute`), or by a super-admin with an audited record in `audit_events`.
- **Zero Default Passwords**: No default credentials (e.g. `admin@nexoranexus.com / admin123`) may ever be committed, seeded, or deployed.

### 2.2 Password Hashing (Cloudflare Runtime Compatible)
- Standard: **PBKDF2-HMAC-SHA256** using the native Web Crypto API (`crypto.subtle`).
- Parameters:
  - Iterations: `100,000` minimum.
  - Salt: Cryptographically secure random 16 bytes (`crypto.getRandomValues(new Uint8Array(16))`), encoded as hex.
  - Key length: 256 bits (32 bytes).
- No home-grown cryptographic algorithms.

### 2.3 Session Management & Token Revocation
- **Session Identifier**: 256-bit entropy random token (`crypto.getRandomValues(new Uint8Array(32))`), stored in D1 as a SHA-256 hash in `user_sessions`.
- **Cookie Security**:
  ```http
  Set-Cookie: __Host-nexora_session=<token>; Path=/; Secure; HttpOnly; SameSite=Strict; Max-Age=604800
  ```
- **Explicit Expiry & Revocation**: Every session record includes `expires_at` (default 7 days) and `revoked_at`. Logout and security-critical events (password changes) immediately set `revoked_at = datetime('now')`.

### 2.4 CSRF Protection
- All state-changing mutations (`POST`, `PUT`, `DELETE`, `PATCH`) require:
  1. Strict `Origin` and `Sec-Fetch-Site` header verification matching the application origin.
  2. Double-submit CSRF token (`X-CSRF-Token` header matching a cryptographically signed cookie).
  3. `SameSite=Strict` cookie policy.

## 3. Data Integrity & Financial Controls

### 3.1 Integer Currency Handling
- Floating-point representations (`199.99`) are strictly prohibited in application logic and database columns.
- All monetary amounts are recorded in **integer paise** (`19999` paise = ₹199.99).
- Application code multiplies and rounds during conversion; database check constraints enforce `amount_paise > 0`.

### 3.2 Payment Verification & Secrets Isolation
- Gateway webhooks and client callback verifications must compute the HMAC-SHA256 signature using `crypto.subtle` and verify it against `razorpay_signature`.
- **Prohibited Data**:
  - Raw credit/debit card numbers (PANs)
  - CVV / CVC security codes
  - UPI PINs or MPINs
  - Internet banking credentials
- Sensitive secrets (`RAZORPAY_KEY_SECRET`, session signing keys) must reside only in Cloudflare encrypted Worker secrets (`wrangler secret put`), never in source code or `wrangler.toml`.

### 3.3 Server-Controlled Program Pricing
- The client-side application never provides the price for an internship program or application order.
- The Worker queries `internship_programs.price_paise` server-side when generating payment orders. Any client attempt to tamper with order pricing is impossible by architecture.

## 4. Academic & Credentialing Integrity

### 4.1 Strict Certificate Issuance Logic
- **Payment Does Not Equal Completion**: Payment only unlocks access to program curriculum, resources, and task submission.
- Certificates can **never** be generated based on payment events.
- Certificate generation requires:
  1. 100% completion of mandatory tasks in `tasks`.
  2. Mentor submission review verdict marked `approved` in `reviews`.
  3. Administrative sign-off in `completion_approvals` with `all_tasks_verified = 1`.
  4. Unique cryptographically random or formatted certificate ID (`NEX-2026-XXXXX`).

### 4.2 Private Artifact Storage (Cloudflare R2)
- Resumes submitted by applicants and generated certificate PDFs must be stored in a **private** R2 bucket (public bucket access disabled).
- Documents are accessed solely through:
  - Short-lived presigned URLs (e.g. 5 minutes expiry) generated by an authenticated Worker for authorized mentors/admins.
  - Authenticated streaming via Worker after role verification.

## 5. Input Validation, SQL Safety & Information Disclosure

### 5.1 Parameterized Queries
- All database interactions with D1 must use prepared statements with parameter binding:
  ```javascript
  const stmt = env.DB.prepare('SELECT id, email, password_hash, password_salt, role FROM users WHERE email = ?').bind(normalizedEmail);
  ```
- Direct string concatenation or template literal interpolation into SQL strings is forbidden.

### 5.2 Information Leakage Prevention
- Public error responses must always return standardized JSON envelopes:
  ```json
  {
    "error": {
      "code": "ERROR_CODE",
      "message": "Safe human-readable description"
    }
  }
  ```
- Stack traces, database column names, internal IDs, and runtime versions must never be exposed to clients.

## 6. Authentication Implementation & Anti-Enumeration Patterns (Phase 22)

### 6.1 Constant-Time Timing Mitigation
- In `POST /api/auth/login`, if an email does not exist in `users`, the server executes `performDummyPasswordCheck(password)` with a precomputed fixed salt. This equalizes the PBKDF2 calculation time (~50ms) to ensure timing side-channels cannot reveal whether an email address is registered.
- Failed logins return identical generic `{"error": {"code": "INVALID_CREDENTIALS", "message": "Invalid email or password"}}` responses regardless of whether the email or password was mismatched.

### 6.2 Password Reset Integrity & Honest Disclosure
- When an email delivery service is unconfigured in production, `POST /api/auth/forgot-password` returns HTTP 503 `EMAIL_SERVICE_NOT_CONFIGURED` to prevent fake-success claims.
- When an email provider is configured or in test environments, single-use reset tokens are generated and stored as SHA-256 hashes in `password_resets` with 1-hour expiry.
- Reset completion immediately revokes all active sessions for the user across all devices.

### 6.3 Brute-Force Login Throttling
- Failed attempts are recorded in `audit_events` (`action: 'auth.login_failure'`).
- The login endpoint queries recent failures within a 15-minute rolling window using composite indexes `idx_audit_events_throttle` and `idx_audit_events_ip_throttle`.
- Exceeding 5 failures results in HTTP 429 `TOO_MANY_REQUESTS`. Empty/null IP addresses do not cross-throttle unrelated users.

### 6.4 Multi-Layered CSRF Defense
- State-changing API mutations (`POST`, `PUT`, `DELETE`, `PATCH`) enforce:
  1. `Origin` header match with worker origin. Opaque/sandboxed `Origin: "null"` is strictly rejected.
  2. `Sec-Fetch-Site` header check (blocks `cross-site`).
  3. `Sec-Fetch-Mode` header check (blocks `navigate` to prevent top-level form submission attacks).
  4. When authenticated via session cookie, requests require a custom header (`X-CSRF-Token` or `X-Requested-With`), which cannot be forged across origins by standard HTML forms or embedded tags.

### 6.5 Email Verification Enforcement
- Accounts are created in `status = 'pending_verification'`.
- Login is blocked with HTTP 403 `EMAIL_NOT_VERIFIED` until the account is verified.
- Protected endpoints reject unverified accounts. Controlled admin activation is supported until a transactional email provider is selected.

## 7. Deep Authentication Security Hardening (Phase 23)

### 7.1 Atomic User Registration
- Registration uses `db.batch([insertUserStmt, insertProfileStmt, insertAuditStmt])` ensuring all-or-nothing atomicity.
- Eliminates orphaned user records in the event of profile insertion failure.

### 7.2 Password Input Bounds & DoS Mitigation
- Passwords are bound between 8 and 128 characters. Passwords exceeding 128 characters are rejected with HTTP 400 `PASSWORD_TOO_LONG`.
- JSON request payloads are capped at 64 KB (`PAYLOAD_TOO_LARGE`, HTTP 413) to prevent memory buffering and CPU exhaustion during PBKDF2 derivation.

### 7.3 Session Fixation Mitigation
- When a user logs in with an existing session cookie presented, the prior session is immediately revoked in `user_sessions` before issuing a fresh 256-bit token.

### 7.4 Complete Password Reset Architecture
- Table `password_resets` stores single-use token hashes with 1-hour expiry.
- Calling `POST /api/auth/reset-password`:
  1. Verifies token hash, unexpired status, and `used_at IS NULL`.
  2. Validates new password complexity.
  3. Updates password hash and salt in `users`.
  4. Marks `used_at = datetime('now')`.
  5. Revokes all active sessions for that user across all devices.
  6. Reusing a spent token returns HTTP 400 `INVALID_OR_EXPIRED_TOKEN`.
